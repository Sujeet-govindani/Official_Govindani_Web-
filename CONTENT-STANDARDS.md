# Content standards — govindaniit.com

Read this in full before writing anything. It is the quality bar every article
is measured against. If an article cannot meet it, do not publish that article.

## NON-NEGOTIABLE RULES

1. NO HIDDEN TEXT. Never white-on-white, display:none, zero-height, tiny fonts,
   or text positioned off-screen. Never keyword-stuff. This is an explicit
   Google spam violation and risks a site-wide manual action that would undo
   every gain. Brand mentions must be visible to a human reader.

2. NO INVENTED FACTS. Never fabricate statistics, client names, project values,
   award claims or dates. If a figure cannot be sourced, give a defensible
   range or write a clearly marked TODO. A gap is recoverable; a fabricated
   number in a client-facing article is not.

3. NO PADDING. If five genuinely distinct, well-researched articles are not
   achievable on a given day, publish fewer and say so in the commit message.
   Scaled low-value content is precisely what Google penalises. Four good
   articles beat five thin ones, every time.

4. EVERY ARTICLE MUST BE DISTINCT. No shared boilerplate paragraphs between
   articles. No reused "Why Choose Govindani Infotech" block. Each piece
   answers a different question for a different reader.

## STRUCTURE (every article)
- 2,500-3,500 words
- Answer the title's question in the first paragraph, then go deeper
- Exactly ONE h1 (the title); proper h2/h3 beneath it
- Unique title tag and meta description; the target phrase in the title,
  the opening paragraph, and one h2 — naturally, never forced
- 2-4 internal links to genuinely relevant pages (/services/..., /pages/ngopage/,
  /whatsapp/...). Link because it helps the reader, not to hit a count.
- Article/BlogPosting JSON-LD
- Real specifics: prices in rupees, timelines, what is included vs excluded,
  worked examples. The existing "NGO Website Cost in India" article is the
  reference for depth and tone.

## BRAND INTEGRATION — VISIBLE ONLY
Permitted: an author bio, a closing CTA block, internal links, and honest
references to work we have actually done. That is the whole list.

## BEFORE COMMITTING
- Does each article read as though a knowledgeable person wrote it for a
  specific reader with a specific problem?
- Is every number either sourced or marked TODO?
- Is there any text a crawler sees that a human does not? (must be no)
- Would you be comfortable if a prospective client read this article?
If any answer is wrong, fix it or drop that article.

## HOUSEKEEPING
- Add each published article to public/sitemap.xml, only once its content exists
- Do not build or deploy. Commit and push; GitHub Actions builds, prerenders,
  verifies and deploys.
